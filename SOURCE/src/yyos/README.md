# Experimental YYOS management

**Authenticated management, native streaming and optional key-only SSH passed short normal-cold-boot checks on this exact profile. Legacy native configuration remains blocked; the SSH-guarded setup path passed a short device trial.** The [24-byte-password reboot loop and verified recovery](https://github.com/dev-zetta/LSCamoflash/blob/main/docs/yyos-recovery.md), controlled 15-byte trial and [enabled normal-boot acceptance](https://github.com/dev-zetta/LSCamoflash/blob/main/docs/yyos-native-media.md#native-enabled-normal-boot-short-acceptance) are separate evidence. Recorded microphone sound and owner-reported Tuya app connectivity passed. The earlier crash cause is unproven; direct VLC live playback, detailed app/recording behavior, repeated boots and long-term stability remain unresolved.

The separate host helper implements fresh SSH identity, independent enable-flag/listener checks and durable private journals. A separately journaled disable/setup sequence retaining the existing 15-byte password passed on this camera after the final status check was moved to a fresh read-only connection. Legacy configuration remains blocked. This management payload is not a recovery procedure.

This separate payload is for the observed LSC 3225722 / SZ F26312, firmware V14.1.5, AK3918AV130 and exact `/appfs/bin/yy_cam` SHA256 `d76d632f41453f53d9d117582fc47073934f5e6ec9a9b7a0ebb1dd3824f6cba7`. It requires `/mnt/sdcard/LSCamoflash-yyos` on the verified writable VFAT `/dev/mmcblk0p1`. Another unit or binary must pass its own investigation; do not bypass these fixed guards.

The payload provides an authenticated HTTP dashboard on port8080, backed by a static ARMv5 BusyBox, read-only status and a recording download helper. A separately provisioned, regular `httpd.conf` outside `www/` must contain exactly one supported hashed account. There is no default password. The Recordings view browses the stock SD hierarchy and downloads raw completed `.media` segments with their session `.info`. Convert supported unencrypted recordings on your computer using the [recording guide](https://github.com/dev-zetta/LSCamoflash/blob/main/docs/yyos-recordings.md). An optional [Controls tab](https://github.com/dev-zetta/LSCamoflash/blob/main/docs/yyos-controls.md) uses a separately provisioned local key for indicator/timestamp switches, fixed 200ms cardinal steps and manual Stop; it defaults disabled without that key. Browser playback, resumed downloads, deletion, a shell endpoint, reboot, firmware updates, overlays, encoding and an additional ONVIF/discovery daemon are unavailable.

Start it manually with its static BusyBox and `start.sh`; use `stop.sh` to stop only the matching owned HTTP process. PID, executable, full arguments and process start time must match before a signal is sent. Existing state and unknown payload files are refused. A failed start retains state if its owned HTTP child cannot be confirmed stopped. `startup.log` contains only bounded fixed lifecycle messages. Keep site credentials and private evidence outside the served directory, and stop the owned service before replacing the payload.

The Streams view displays allowlisted native RTSP and ONVIF addresses with an explicit public-configuration block. The controlled trial and subsequent normal boot accepted short decoding and RTSP Digest/ONVIF WSSE controls. Recorded microphone sound was accepted before that boot; post-boot audio decoded with zero samples. The web account does not protect other camera services. No status request enables or changes a native service. HTTP Basic authentication does not encrypt traffic; this experimental interface is intended for a trusted LAN.

The source shares the project's lightweight Fullhan interface design but uses an isolated YYOS profile and payload inventory. Project code and third-party components retain their separate notices. Owned HTTP stop/restart and authenticated recording downloads passed after a guarded remote update, and the recording browser passed desktop/mobile page checks. Detailed app/recording behavior, stable repeated cold boots and long-term use remain unverified. Every changed runtime requires its own device acceptance.
