# LSC Smart PTZ 3007325.5 / SI L25502

This fork adds an **experimental runtime profile** for the exact stock firmware below. Its SD-based firmware backup, normal-mode SD boot, Wi-Fi connection, web UI login and local RTSP video/audio decoding have been physically verified; the user also confirmed audible microphone sound. ONVIF Device/Media SOAP requests return the H.264 substream correctly through a manual connection. Automatic discovery requires a separate component; detailed audio/video synchronization, custom PTZ and long-term operation remain unverified. Build and fixture tests establish software behavior separately from these device observations.

Three physical normal-mode runtime boots did not provide app access or a DHCP lease. The first created backups and the overlay, but its RAM logs were lost when power was removed. On the second, all 745 built payload files matched the card, persistent logs recorded init returning status 0 in roughly one minute, and no reboot was observed. Stock pairing and app access worked with the SD card removed. An init exit status of 0 does not establish that the subsequent stock application started or connected.

The third test retained one stock application PID across the handoff samples, and the camera tracked motion, while WLAN disappeared after init. WPA appeared transiently, no DHCP lease was observed, and stock logging reported an all-zero MAC value. These observations show application activity alongside a network failure; they do not establish that the stored hardware MAC changed. A concrete missing-tool defect was identified and subsequently corrected in the runtime overlay, as described below.

The fourth test, after restoring the stock network-tool aliases, connected successfully. The handoff samples recorded `wlan0` up, WPA state `COMPLETED`, address `192.168.88.12` and a default route; the user confirmed working web UI login on port 8080. This accepts normal-mode Wi-Fi and web UI startup for the tested card. Tuya app functions, recordings and local streaming require their own checks.

## Runtime changes

The first-partition `hostapd` is now a static ARM native entry that verifies the visible writable FAT/MMC mount, including stock firmware's covered tmpfs entry at `/mnt`. It executes the supplied static BusyBox and `bootstrap.sh` through verified file descriptors. It replaces the original process before the stock ATBM station script's `killall hostapd`, then the shell stage explicitly reloads the station driver on this exact revision. A failed runtime mount stops setup.

The boot stage prefers the traditional second FAT partition. It also accepts `HACK/` on the boot FAT card and retains that card with a bind mount at `/tmp/sd`, allowing stock startup to unmount `/mnt`. It loads card settings before applying a staged update and stops runtime startup if that installation fails. The updater handles both layouts, replaces running executables through temporary files and renames, retains a staged update after mount/copy/sync failures, and avoids writing boot files into the covered tmpfs. Older checksum configuration files remain usable when updating without replacing `HACK/etc`.

The exact profile verifies SHA-256 in addition to MD5, records model, sensor and video metadata, and keeps the matching stock `anyka_ipc`. It clears an incompatible cached generated patch, disables IPS application for this profile and bypasses alternate patched/static executables on watchdog restarts. No patch or motor address from an older camera is reused. Toolkit PTZ capability stays disabled; the camera's motor hardware is recorded separately, and its calibration is not rewritten.

For this profile, init copies the current stock `/etc/config/_ht_sw_settings.ini` to the SD configuration without changing its bytes. It skips the generic software-settings template, sanitization and deduplication, preserving the stock schema rather than adding keys from unrelated cameras. This does not undo configuration changes made during an earlier boot.

For this exact profile, the overlay now retains the stock BusyBox aliases at `/sbin/ifconfig` and `/sbin/udhcpc`. The prior init explicitly removed those two stock PATH entries before binding the overlay over `/sbin`, leaving stock network startup without either command. Running the recovered stock BusyBox ash under ARM926 with a PATH lacking the aliases returned status 127 for both bare commands, confirming that the shell does not provide an applet fallback. An empty stock `ifconfig.txt` from the third test corroborates the missing command path. Other profiles retain their previous overlay behavior. The fourth test established Wi-Fi and web UI recovery after this correction.

## Build and stage

Download `LSCamoflash-2.01.0000-uclibc.tar.gz` and `SHA256SUMS` from [v2.01.0000](https://github.com/dev-zetta/LSCamoflash/releases/tag/v2.01.0000) and follow [Installation](installation.md). For a local build, follow [Building and testing](building.md); upstream packages do not contain these changes.

For the traditional layout, use the built `SOURCE/build/mmcblk0p1/` and `SOURCE/build/mmcblk0p2/` contents with the existing two-partition procedure. For a spare single FAT32 card, copy the **built** `mmcblk0p2/` contents, including `HACK/`, to its root, then the **built** `mmcblk0p1/` contents. A whole-device FAT32 card is accepted by the tested stock mount script. Copying source templates alone omits the native launcher, static BusyBox and compiled services. The single-FAT runtime card has passed physical normal-mode Wi-Fi/web UI tests and local-mode RTSP video/audio tests after reboot. Full Tuya app functions, recording and long-term operation remain separate acceptance checks.

Use a separate card or archive the backup kit's root files before staging the runtime. Both kits own the root `hostapd` filename. Preserve your verified firmware backup on the host before making runtime changes, and safely eject the card before booting the camera.

## First boot and diagnostics

First initialization creates backups and an SD overlay, so it can take several minutes and may request a reboot after a 60-second delay when setup changes require one. Stock startup waits synchronously for this hook. Init now runs through the supplied static BusyBox with a 600-second deadline and a five-second forced-kill grace period. This bounds init under normal process scheduling; it does not cover the preceding station reload, staged update or custom pre-init hooks, and cannot guarantee a deadline for uninterruptible kernel I/O.

Once init reaches services, it checks that the supervisor remains alive and waits up to 45 nominal one-second polls for first readiness. A supervisor exit or readiness timeout before that marker stops init instead of leaving the stock startup waiting indefinitely. Each service invocation also has a 60-second timeout with a five-second forced-kill grace period. These limits bound software wait paths; they do not establish successful stock application startup or connectivity.

After the runtime card is mounted, bootstrap creates persistent diagnostics before reloading the station driver. In either card layout, inspect these paths relative to the runtime card root:

- `HACK/var/log/boot.log`: bootstrap progress and init exit status; previous boot in `boot.previous.log`.
- `HACK/var/log/init.log` and `init.err`: init output and errors; previous boot in `init.previous.log` and `init.previous.err`.
- `HACK/var/log/services-startup.log`: first service invocation output, capped at 64 KiB; the previous attempt is `services-startup.previous.log`.

The boot and init logs retain one previous boot but have no byte cap. The camera clock can start in 2000, so use current/previous rotation and captured progress rather than timestamps alone. Missing logs do not prove that the native hook never ran: logging starts only after the runtime mount succeeds. On init failure, bootstrap attempts to release only a matching application-wrapper bind and a setup lock created during that invocation; it does not roll back every mount, network change, persistent setting or custom hook.

The previous service log reader had a demonstrated buffering gap: `head` could hold output below 4 KiB while a background daemon retained the pipe's write end. The reader now uses `dd` with `iflag=count_bytes` to write short reads immediately while retaining at most 64 KiB. This fixes diagnostic loss; it does not identify the cause of the second boot's offline state.

For an opt-in diagnostic boot, create an **empty `_ht_get_log.conf` file on the boot card root**, beside `hostapd` and `_ht_ap_mode.conf`. In the traditional layout this is partition 1; in the single-FAT layout it is the shared card root. Stock firmware copies this marker to `/tmp`, keeps `/mnt` mounted, and writes its own `ht_log/` directory on the boot card. Its 5 MB rotation threshold does not cap total log storage.

When this marker is present and init returns status 0, bootstrap starts the bounded `HACK/sbin/boot_diagnostics.sh` sampler in the background. It queries filtered process, memory, network and WPA states at nominal offsets of 0, 5, 15, 30 and 60 seconds without changing those states. Its output is `HACK/var/log/handoff.log`, with the previous run in `handoff.previous.log`. The third physical test exercised this diagnostic path and distinguished a persistent stock application process from the later WLAN failure; the fourth recorded successful WPA, DHCP and route recovery after the alias correction.

The same opt-in marker enables `HACK/var/log/wrapper-status.log`, retaining the previous wrapper invocation in `wrapper-status.previous.log`. It records phases including entry, configuration loaded, identity verified, lock handling and `exec-stock`, while preserving the PID used to execute the stock binary. The `exec-stock` phase records intent immediately before exec; it does not prove that exec succeeded or that the application became usable.

Power the camera off before removing the card. Preserve a private host copy of current and previous runtime logs, boot-root `ht_log/`, `HACK/backup/` and relevant generated configuration before another attempt or card overwrite replaces the evidence. Raw stock logs can contain credentials and device or account identifiers; the filtered sampler and wrapper status are designed to omit secrets, but review all evidence before sharing it. Remove the boot-root `_ht_get_log.conf` and cold-boot to disable opt-in stock logging and handoff diagnostics. Test stock pairing without the runtime card separately, and do not infer a fixed root cause from a successful build, an init status or a wrapper phase.

## Stock Tuya or local RTSP

Normal mode retains the unmodified stock application and lets Tuya reconstruct its paired Wi-Fi settings. Leave both `local_rtsp_only` and `wifi_config_override` unset when testing that path; the explicit Wi-Fi example below is for local RTSP. Pairing and app access without the SD card, and Wi-Fi and web UI access through the runtime card, have been verified. Direct local RTSP is opt-in and replaces the normal Tuya application mode; simultaneous Tuya cloud operation is not established. Generating a local stream link in the web UI does not switch modes or start the stock RTSP server.

For a first local RTSP boot, put the following in the card's `HACK/etc/hack_custom.conf`, replacing the example Wi-Fi values for a WPA2-Personal network:

```sh
export local_rtsp_only="1"
export wifi_config_override="1"
export wifi_driver="nl80211"
export wifi_ssid="YOUR_SSID"
export wifi_scan_ssid="1"
export wifi_key_mgmt="WPA-PSK"
export wifi_pairwise="CCMP"
export wifi_group="CCMP"
export wifi_psk="YOUR_PASSPHRASE"
export wifi_use_dhcp="1"
```

Keep that file private. The paired network is stored in an encrypted stock database; the plaintext `/tmp/wpa_supplicant.conf` is normally reconstructed by Tuya startup. Direct RTSP mode bypasses that startup. Without an explicit override, the network helper can reuse an existing RAM WPA file, but fails clearly when none exists. Association is bounded and init stops after a failed network handshake. A DHCP lease and actual LAN reachability still need to be checked on the camera.

On this exact binary, `/tmp/_ak39_factory.ini` selects manufacturing tests that can replace networking. Local mode therefore uses the separate RAM `/tmp/_ht_ap_mode.conf` marker, after preparing station networking. The wrapper rejects an unowned manufacturing marker and the old `FORCE_AK39_FACTORY_*` options for this revision. It removes only markers it owns when returning to normal mode; it never writes a local-mode marker to the SD root or flash.

The exact firmware provides these direct RTSP endpoints; both video streams have been decoded on the camera:

| Stream | URL to test | Configured codec |
| --- | --- | --- |
| Main | `rtsp://<camera-ip>:88/videoMain` | H.265, 2304×1296 |
| Sub | `rtsp://<camera-ip>:89/videoSub` | H.264, 640×360 |

The web link and local stream API use these endpoints for this profile. The bundled ONVIF server supports H.264 and advertises the substream; it must not label the H.265 main stream as H.264. The live check decoded 60 frames from each stream over both RTSP/TCP and RTSP/UDP at 15 frames per second, confirming main H.265 at 2304×1296 and sub H.264 at 640×360. These requests needed no RTSP credentials. Endpoint selection, codec metadata, CGI responses and ONVIF startup arguments are also covered by offline tests. Keep the camera on the intended LAN while testing.

Both streams carry mono PCMA (G.711 A-law) audio at 8 kHz. The first video-only helper advertised that track but delivered zero audio packets. Common stock startup already initializes the microphone and G.711 A-law encoder; mode 2 skips the normal startup that installs its forwarding callback. The helper now registers a channel-0 encoded audio callback that passes the borrowed buffer and original 64-bit millisecond timestamp directly to the stock sender, which forwards it to both RTSP sessions. The raw audio callback used by Tuya remains unset, and no extra encoder or capture thread is created.

After installing the revised helper on the SD card and rebooting, four approximately eight-second live checks decoded 64,512–64,768 audio samples alongside 105–112 video frames: both endpoints over TCP and UDP. All four FFmpeg runs exited zero with completed progress, and signal statistics showed non-silent audio. No recording was saved. The user then confirmed audible microphone sound in the H.265 main stream. Detailed audio quality, audio/video synchronization and long-term behavior remain separate acceptance checks.

The bundled ONVIF server advertises `http://<camera-ip>:5000/` as its service address. Add that HTTP address, or the camera IP and port 5000, manually in an ONVIF client. The bundled `onvif_srvd` does not implement WS-Discovery and this build does not include the separate `wsdd` daemon, so automatic discovery is unavailable. The web UI now returns this SOAP service address instead of a custom `onvif://` display URI. ONVIF startup waits for a supported RTSP listener. Live `GetSystemDateAndTime`, `GetCapabilities`, `GetProfiles` and `GetStreamUri` requests returned HTTP 200 without SOAP faults; the only profile was H.264 640×360 and its URI selected port 89 `/videoSub`. A generated URL alone does not establish successful streaming. DHCP may assign a different address after a mode change.

Remove `local_rtsp_only` and its Wi-Fi override when returning to stock-managed pairing, then cold-boot. Disabling a runtime mode removes only its owned RAM markers. To stop the SD hook entirely, remove or archive the root `_ht_ap_mode.conf` marker while the camera is off; stock startup's persistent AP-copy effects are described in the backup guide.

## Binary evidence and acceptance

The exact `anyka_ipc` exports symbols, allowing bounded inspection without executing it. Its mode selector at `0x000ce228` checks `_ak39_factory.ini` before `_ht_ap_mode.conf`. Main's mode-2 branch at `0x000cea18` calls `ht_rtsp_start` (`0x000bda44`) without the normal Tuya networking branch. The RTSP worker (`0x000bd6e0`) starts the server (`0x000bd0c8`), creates listeners on decimal ports 88 and 89, and registers `/videoMain` and `/videoSub`. Configuration initialization (`ht_config_init`, `0x0008af24`) supplies the hardware settings to RTSP; the captured hardware settings select main encoder 2 (H.265) and sub encoder 0 (H.264). These offsets apply only to the binary with the recorded SHA-256 and are evidence for the profile, rather than instructions for patching another binary.

The first physical local-mode test opened both RTSP ports, but neither answered `OPTIONS` or `DESCRIBE` within four seconds. Both player attempts failed. A live shell confirmed the exact executable hash, the local-mode RAM marker and active encoder/RTSP threads. Static inspection found the missing initialization: the encoder callbacks remain NULL in mode 2, while `rtsp_do_event` is reached only when a video frame is forwarded. The normal Tuya capture setup installs callbacks but also relies on Tuya ring buffers that this mode never initializes.

The local-mode launcher now requires the small `HACK/lib/libcamoflash_rtsp.so` preload for this exact firmware. The launcher verifies the complete stock binary SHA-256 before loading it; the helper additionally checks the executable layout, critical instructions and exported symbol addresses. It waits at the existing main-loop sleep call for both RTSP servers and sessions, then publishes two video callbacks and one encoded audio callback that forward the stock buffers and original 64-bit millisecond timestamps directly to the stock RTSP senders. It creates no helper thread and calls no Tuya capture API. Its scope is the stock application process in this explicit local mode.

Dependency constructors can call an interposed function before the helper constructor runs. Real libc functions are therefore resolved through `pthread_once` at first use, before any pass-through call. An earlier candidate returned `EINVAL` for an early mutex call and failed on the camera with kernel OOM; a dependency-constructor fixture now checks successful locking and actual exclusion between threads before the helper constructor. The revised helper starts successfully and installs its callbacks on the camera.

Encoded audio uses setter `ht_audio_codec_set_get_aenc_cb` at `0x000a915c`, channel-0 callback slot `0x00534954` and sender `ht_rtsp_send_audio_frame` at `0x000bcfd0`. Its ABI is `void(void *data, int32_t bytes, uint64_t timestamp_ms)`; the sender performs the timestamp conversion and fanout. The producer holds its codec mutex while calling the helper. Registration is therefore one-time publication into an empty slot: replacing or clearing it while holding the helper lifecycle mutex would invert the lock order. Audio shares the video lifecycle guard, and the exact-binary checks also verify its setter, producer and sender instructions.

The helper serializes frame forwarding and disables it before the stock stop path frees RTSP objects. Published callbacks remain mapped for the process lifetime: the encoder checks and reloads callback pointers separately, so clearing them while it runs could cause a NULL call. The helper therefore leaves disabled callbacks in place until process exit. These firmware-specific safeguards and fixtures require live streaming acceptance as described below; they do not establish compatibility with a different binary.

Normal-mode SD boot, Wi-Fi connection, web UI login and removal-of-card recovery have been observed. Local-mode SD startup after a full reboot, both RTSP video streams and manual ONVIF substream selection have also been observed. Audible local microphone audio has also been confirmed. Remaining camera acceptance includes normal-mode Tuya app and recording functions, detailed audio/video synchronization, a separate power-off/on cycle and long-term or multiple-client streaming. Custom PTZ remains disabled until an exact revision-specific control backend is validated. Neither a verified backup nor QEMU execution proves those remaining outcomes or a working flash restore.

## Memory reporting

The original RAM bar used total memory minus `MemFree`, so occupied filesystem cache contributed to the displayed percentage. It now uses total minus `MemAvailable`, the kernel estimate of memory allocatable without swapping, and shows available memory alongside cache, buffer, reclaimable-slab and shared-memory counters. Those breakdown counters overlap and must not be added together as separate allocations. If `MemAvailable` is missing or invalid, the UI explicitly labels its free-memory fallback. See the [Linux proc documentation](https://www.kernel.org/doc/html/latest/filesystems/proc.html) for the counter definitions.

The user-observed 90% reading alone does not establish memory pressure, and changing its calculation does not free memory. Opt-in handoff diagnostics now preserve numeric memory counters and selected process resident-memory observations. The first local-mode live measurement recorded 32,648 KiB total and 9,588 KiB available, about 29% available; this is one observation before the RTSP callback fix. After the video-only helper SD reboot and stream checks, the camera reported 8,128 KiB available (about 25% of total), the application had 26 threads and 6,460 KiB resident, and the kernel had recorded no OOM event since that reboot. These snapshots do not establish long-term memory behavior.

Before the audio update, a later snapshot recorded one application OOM event with roughly 17.8 hours of uptime; that event predates the audio helper and remains outside the short acceptance checks. After installing audio support and rebooting, all four audio/video checks completed and a snapshot recorded 8,096 KiB available, application RSS 6,784 KiB, 26 threads and zero kernel OOM events since that reboot. This does not establish long-term memory stability.
