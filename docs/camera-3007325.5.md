# LSC Smart PTZ 3007325.5 / SI L25502

This fork adds an **experimental runtime profile** for the exact stock firmware below. Its SD-based firmware backup has been physically verified. Runtime installation, decoded RTSP frames, ONVIF discovery and custom PTZ movement have not yet been accepted on the camera. Build and fixture tests establish the software behavior, rather than those physical outcomes.

## Runtime changes

The first-partition `hostapd` is now a static ARM native entry that verifies the visible writable FAT/MMC mount, including stock firmware's covered tmpfs entry at `/mnt`. It executes the supplied static BusyBox and `bootstrap.sh` through verified file descriptors. It replaces the original process before the stock ATBM station script's `killall hostapd`, then the shell stage explicitly reloads the station driver on this exact revision. A failed runtime mount stops setup.

The boot stage prefers the traditional second FAT partition. It also accepts `HACK/` on the boot FAT card and retains that card with a bind mount at `/tmp/sd`, allowing stock startup to unmount `/mnt`. It loads card settings before applying a staged update and stops runtime startup if that installation fails. The updater handles both layouts, replaces running executables through temporary files and renames, retains a staged update after mount/copy/sync failures, and avoids writing boot files into the covered tmpfs. Older checksum configuration files remain usable when updating without replacing `HACK/etc`.

The exact profile verifies SHA-256 in addition to MD5, records model, sensor and video metadata, and keeps the matching stock `anyka_ipc`. It clears an incompatible cached generated patch, disables IPS application for this profile and bypasses alternate patched/static executables on watchdog restarts. No patch or motor address from an older camera is reused. Toolkit PTZ capability stays disabled; the camera's motor hardware is recorded separately, and its calibration is not rewritten.

## Build and stage

Build this fork; upstream download packages do not contain these changes:

```sh
make -C SOURCE all release update
```

For the traditional layout, use the built `SOURCE/build/mmcblk0p1/` and `SOURCE/build/mmcblk0p2/` contents with the existing two-partition procedure. For a spare single FAT32 card, copy the **built** `mmcblk0p2/` contents, including `HACK/`, to its root, then the **built** `mmcblk0p1/` contents. A whole-device FAT32 card is accepted by the tested stock mount script. Copying source templates alone omits the native launcher, static BusyBox and compiled services. The single-card runtime path is implemented and tested with fixtures; physical runtime acceptance remains pending.

Use a separate card or archive the backup kit's root files before staging the runtime. Both kits own the root `hostapd` filename. Preserve your verified firmware backup on the host before making runtime changes, and safely eject the card before booting the camera.

## Stock Tuya or local RTSP

Normal mode retains the unmodified stock application. Leave `local_rtsp_only` unset to use that path. Direct local RTSP is opt-in and replaces the normal Tuya application mode; simultaneous Tuya cloud operation is not established.

For a first local RTSP boot, put the following in the card's `HACK/etc/hack_custom.conf`, replacing the example Wi-Fi values for a WPA2-Personal network:

```sh
export local_rtsp_only="1"
export wifi_config_override="1"
export wifi_driver="nl80211"
export wifi_ssid="YOUR_SSID"
export wifi_scan_ssid="1"
export wifi_key_mgmt="WPA-PSK"
export wifi_pairwise="CCMP"
export wifi_group="CCMP"
export wifi_psk="YOUR_PASSPHRASE"
export wifi_use_dhcp="1"
```

Keep that file private. The paired network is stored in an encrypted stock database; the plaintext `/tmp/wpa_supplicant.conf` is normally reconstructed by Tuya startup. Direct RTSP mode bypasses that startup. Without an explicit override, the network helper can reuse an existing RAM WPA file, but fails clearly when none exists. Association is bounded and init stops after a failed network handshake. A DHCP lease and actual LAN reachability still need to be checked on the camera.

On this exact binary, `/tmp/_ak39_factory.ini` selects manufacturing tests that can replace networking. Local mode therefore uses the separate RAM `/tmp/_ht_ap_mode.conf` marker, after preparing station networking. The wrapper rejects an unowned manufacturing marker and the old `FORCE_AK39_FACTORY_*` options for this revision. It removes only markers it owns when returning to normal mode; it never writes a local-mode marker to the SD root or flash.

Static inspection identifies these direct RTSP endpoints:

| Stream | URL to test | Configured codec |
| --- | --- | --- |
| Main | `rtsp://<camera-ip>:88/videoMain` | H.265, 2304×1296 |
| Sub | `rtsp://<camera-ip>:89/videoSub` | H.264, 640×360 |

The web link and local stream API use these endpoints for this profile. The bundled ONVIF server supports H.264 and advertises the substream; it must not label the H.265 main stream as H.264. Endpoint selection, codec metadata, CGI responses and ONVIF startup arguments are covered by offline tests. Successful frame delivery, negotiated resolution, authentication behavior and discovery require a device test. Keep the camera on the intended LAN while testing.

Remove `local_rtsp_only` and its Wi-Fi override when returning to stock-managed pairing, then cold-boot. Disabling a runtime mode removes only its owned RAM markers. To stop the SD hook entirely, remove or archive the root `_ht_ap_mode.conf` marker while the camera is off; stock startup's persistent AP-copy effects are described in the backup guide.

## Binary evidence and acceptance

The exact `anyka_ipc` exports symbols, allowing bounded inspection without executing it. Its mode selector at `0x000ce228` checks `_ak39_factory.ini` before `_ht_ap_mode.conf`. Main's mode-2 branch at `0x000cea18` calls `ht_rtsp_start` (`0x000bda44`) without the normal Tuya networking branch. The RTSP worker (`0x000bd6e0`) starts the server (`0x000bd0c8`), creates listeners on decimal ports 88 and 89, and registers `/videoMain` and `/videoSub`. Configuration initialization (`ht_config_init`, `0x0008af24`) supplies the hardware settings to RTSP; the captured hardware settings select main encoder 2 (H.265) and sub encoder 0 (H.264). These offsets apply only to the binary with the recorded SHA-256 and are evidence for the profile, rather than instructions for patching another binary.

The remaining camera acceptance is a cold boot from the built runtime card, normal-mode app/Wi-Fi/recording checks, main and sub RTSP decoding, ONVIF substream discovery, and removal-of-card recovery. Custom PTZ remains disabled until an exact revision-specific control backend is validated. Neither a verified backup nor QEMU execution proves those outcomes or a working flash restore.
