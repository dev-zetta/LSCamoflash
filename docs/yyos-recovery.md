# YYOS guarded recovery: short normal boot passed

The [exact-profile recovery tool](../tools/yyos/recover-native-off.sh) targets the observed **3225722 / SZ F26312 / firmware 14.1.5 / AK3918AV130** camera after the [native-media reboot loop](yyos-native-media.md). It passed **45 offline checks: 37 host and eight ARM926**, and independent review. **The recovery boot, exact edit/private-output verification, host cleanup and one subsequent normal-bootstrap cold boot passed.** The owner reported Online and steady after the normal boot, and read-only HTTP/API/Tuya checks succeeded. This is short physical recovery acceptance, not long-term stability or native-media acceptance. Native enablement remains blocked; this is not a generic deployment recipe.

During the recovery boot, HTTP returned **401 without credentials / 200 with credentials**, the API reported stock app and owned HTTP running, and uptime increased from **151 to 235 seconds** across an 84-second observation. Available RAM was **16,596 then 16,800 KiB**; neither native RTSP nor ONVIF listener was observed. Authenticated Tuya 3.5 status reported **DP237 false / DP239 true**. This establishes native enablement observed off and a password-set indicator, not the exact password or authentication enforcement.

After the debug entry was archived and the known normal management bootstrap restored, the owner confirmed another Online, steady boot at the same LAN address. Read-only checks again returned **HTTP 401/200**, with uptime **137 seconds**, stock app/management running, **17,208 KiB available RAM**, **648 KiB HTTP RSS** and **9,464 KiB stock RSS**. A second normal-boot sample reached **444 seconds**, an increase of **307 seconds**, with stock/management still running, native listeners absent and **16,836 KiB available RAM**. Tuya status remained **DP237 false / DP239 true**. This establishes the observed off state through one normal cold boot and that observation window; repeated-boot endurance, detailed recording and long-term stability remain unverified.

Subsequent static review confirmed [unsafe stock password-cache copies](yyos-native-media.md#why-configuration-is-disabled) and oversized 24-byte password values in the preserved pre-recovery configuration. That is a strong reboot-cause candidate, not proof from a captured crash location. Native activation remains blocked despite the host helper's new 15-byte password ceiling; no further device trial is prepared.

The returned private copy contained **15 files totaling 14,803 bytes**, with two matching host hash readbacks. Status recorded **`CONFIG_OFF_STOCK_START_RETURNED`**, **`config_modified=1`**, **`stock_launch_attempts=1`** and stock exit **0**. Independent host verification established that the **248-byte configuration changed at exactly two bytes**: both native enable flags went from **1 to 0**, with every other byte, including password bytes, preserved. This is verified configuration-off recovery evidence, not a flash-image restore or native-password authentication test.

The reviewed recovery source SHA-256 is `9ee6fc266514ce90f96ec2453211d754c7dae2fd51ab5e8b78af19de3c8380fb`. The staged entry uses the project's native launcher, static BusyBox, recovery `dump.sh`, `yy_debug.ini` and checksums. The normal `yy_telnet_start` marker was archived, all 371 existing files were preserved, and the debug entry was staged last. This debug entry is separate from the normal management and NOR-backup kits; do not mix their markers or treat those kits as recovery payloads.

## Guarded change and handoff

The script requires root, exact hashes for `yy_cam` and the stock init/start scripts, the expected writable MMC/VFAT SD mount, the exact `/config` JFFS2 mount and NOR geometry, and an absent `yy_cam` process. It validates the selected debug entry, rejects symlinked or unsafe paths and uses a retained per-boot RAM lock to prevent a second stock-start attempt. Each operation is bounded, with a 240-second preparation budget; uninterruptible kernel I/O remains outside userspace timeout guarantees.

Its only persistent edit is to **existing `1` values** for `[rtsp] rtsp_on_off` and `[onvif] onvif_on_off` in `/config/param.conf`, replacing those value bytes with **`0`**. Missing flags are treated as default-off and are not added. Passwords and all unrelated bytes remain unchanged. This writes the existing configuration filesystem; it does not erase/program raw MTD, restore a flash image or reset the camera.

Before writing, it preserves the original configuration and metadata privately on SD, verifies their hashes and checks file/directory flushes. The replacement preserves length, formatting, owner and mode, is written through an exclusively created same-filesystem temporary file, flushed and hash-checked, then atomically renamed. The original identity/hash and absence of `yy_cam` are checked again before commit; the configuration directory is flushed and the committed result verified before handoff. Failure can follow a committed configuration change; no automatic rollback is claimed.

If both flags are already off or absent, **`ALREADY_OFF_HOLD_DEBUG`** deliberately holds without editing configuration or starting the stock app. Invalid identity, configuration or pre-handoff state likewise fails closed. Only a verified off edit permits **one** call to the original stock startup script. Its return value and a possible bounded management-start attempt are recorded; neither establishes that the camera became healthy.

## Private evidence and cleanup

Each attempt retains `native-recovery/run-*/` with the original/candidate configuration, plan, metadata, snapshots, logs and status. Keep the whole directory private: configuration and kernel logs can contain credentials, including the earlier native password request. A final **`CONFIG_OFF_STOCK_START_RETURNED`** status means the verified edit and stock-script return completed; the script still records **`physical_recovery_verified=no`**. App reachability, absence of repeated reboots, native listeners and subsequent normal startup require separate checks.

After the steady recovery-boot report, the owner powered off and remounted the card; the private output capture and two-byte edit verification above completed. Host cleanup archived the root recovery debug entry, dumper and checksum set, restored only the known management wrapper/checksums and staged the normal marker last. Native launcher/BusyBox, the existing nested public payload and private authentication identity were checked; **410 preexisting files were preserved**, with no configuration write by cleanup. The card was safely unmounted, and the subsequent normal cold boot passed the short checks above. The known UI payload was retained, deferring deployment of warning-only UI changes to a separate step.

**Do not change `yy_debug.ini` while the camera is powered**: the stock init monitors mode changes and may reboot. Cleanup requires power-off/remount and preservation/verification of the complete private output before archiving the recovery debug entry. The accepted recovery boot, exact edit, host cleanup and one normal bootstrap do not establish long-term stability, repeated-boot endurance or native-media operation. Do not retry native enablement.
