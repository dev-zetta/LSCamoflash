# LSC 3225722 / SZ F26312: investigation in progress

**LSCamoflash runtime support is not implemented or verified for this camera.** The investigation concerns a user-owned unit labelled **SZ F26312**, article **3225722**, with app-reported firmware **V14.1.5**. On **2026-10-15**, an identity-only SD collector successfully identified the running platform, application, mounts and exposed flash geometry. Its output passed host checksum verification after a physical card remount. Firmware backup and local streaming remain unverified. Do not install the existing Anyka or Fullhan runtime packages.

[Action's article 3225722 product page](https://www.action.com/nl-nl/p/3225722/lsc-smart-connect-draaibare-binnencamera/) identifies a rotatable indoor camera marketed with 2K video and 2.4/5 GHz Wi-Fi. This establishes the retail product reference, not its internal hardware or the compatibility of every production revision.

## What the network checks establish

A bounded check of 23 common TCP ports found only **6668** open; the other 22 probes received connection refusals. The tested ports included SSH 22, Telnet 23, HTTP 80/8080, HTTPS 443, RTSP 554/8554 and ONVIF's commonly used port 5000. No shell, web UI, RTSP stream or ONVIF service was reached through those endpoints.

The reference associates port 6668 with the Tuya LAN protocol. Here, only TCP connectivity was checked: no authenticated Tuya command or streaming capability has been demonstrated. This was not a complete port scan or proof that the firmware lacks local video support. A separate 18-second check received no camera-originated Tuya discovery datagrams and no response to one unicast ONVIF discovery probe; lack of a response does not establish that those UDP services are disabled.

## Why existing installers do not apply

The [3007325.5 Anyka profile](camera-3007325.5.md) depends on its exact stock application, boot hooks, firmware identity and media callback behavior. The collected YYOS-style layout and `yy_cam` application require separate integration. A shared Anyka name or ARM926 CPU is insufficient to reuse installers, preload libraries, callback offsets, startup replacements or camera settings.

The [SZ B22705 Fullhan package](camera-sz-b22705.md) targets a different SoC, ARM architecture, stock application and SD mount layout. Its guarded management and ONVIF services are not a package for SZ F26312. Neither existing release package should be copied onto this camera's card as an exploratory installation.

## Verified identity-only SD diagnostics

The [identity-only SD collector](../tools/firmware-backup/collect-yyos-identity.sh) passed 48 offline fixture checks, including 24 forced ARM926 cases with the kit's static BusyBox, before the first physical run. That run confirmed the normal-startup SD entry described by the reference's [boot-chain findings](https://github.com/alex-so-3/lsc-ak3918-yyos-root/blob/06a5b1efd901db762ef74149e6ddb94bc6c254cc/docs/FINDINGS.md#boot-chain-how-the-sd-root-works). Inspection of this unit's collected startup script independently confirmed the `yy_telnet_start` / `telnetd` entry at lines 78–79; normal startup also conditionally launches `yy_cam` when the stock NVRAM `STATUS` is `active`.

The tested payload uses that entry solely to run a bounded diagnostic program and finish. The `telnetd` file is the project's existing [native backup launcher](../tools/firmware-backup/hostapd.c), renamed for the YYOS entry; it starts the identity collector supplied as `dump.sh` through verified file descriptors. The five SD-root files are `telnetd`, `busybox`, `dump.sh`, `yy_telnet_start` and `SHA256SUMS`. Their staged bytes passed SHA-256 readback and file/directory flush checks before the spare card was unmounted.

Despite the entry's name, this payload starts no Telnet daemon or other network listener. It leaves the reference's debug-mode startup replacement unused and does not change authentication or persistent configuration, stop the stock application or alter network routes. It reads flash metadata rather than MTD device contents. The native program and BusyBox were independently verified as static ARMv5TEJ programs, with ARM926 applet and no-SD rejection checks.

The evidence is limited to CPU/kernel/memory identity, fixed startup-script snapshots and full-source hashes, the stock application's path and SHA-256, bounded optional process maps, visible flash metadata, and the mounted SD layout needed to assess a subsequent backup. The collector verifies root access and one visible writable MMC/FAT mount at `/mnt/sdcard`, reserves time within a 60-second monotonic budget, retains unique run directories and records completion or failure. Successful output includes its own SHA-256 inventory and checked file/directory flushes. Keep `backup-launcher.log` and `yyos-identity/run-*/` private; an identity-complete status is not a firmware backup result.

On the first successful boot, the native entry recorded **UID 0 / root**, the accepted `/mnt/sdcard` mount from `/dev/mmcblk0p1`, and **`CHILD_EXIT=0`**. The collector recorded **`IDENTITY_COLLECTION_COMPLETE`**. After the card was physically removed, remounted on the computer and copied to private host storage, **101 checksummed files** passed verification. The owner reported that the camera stayed online during the two-minute attempt and that the app recognized the card's capacity. These observations establish diagnostic execution and identity-output readback; they do not establish streaming, a complete recording test or a firmware backup.

Existing recordings must be preserved before preparing a spare card; the camera's formatting behavior, mount path and executable compatibility must be checked rather than borrowed from another profile. Normal stock startup may itself write persistent state, even when the collector writes only to the SD card.

The public files linked here are the project's collector and launcher source; the captured stock scripts, maps and other device output remain private. This guide contains no shell-enablement or flash-writing procedure. A repeatable firmware backup requires the separate collection and verification steps below.

## Build a separate YYOS NOR kit

The [YYOS builder](../tools/firmware-backup/build-yyos-kit.py) creates a separate host-side package for the generic paired-read NOR collector. **A verified firmware backup is still pending on this camera.** The normal-boot entry and identity-only capture above were physically verified; the ongoing backup attempt uses independently checked native/BusyBox components and a freshly staged collector, not output from this new builder. Do not treat the builder's assembly checks as physical acceptance.

The builder passed nine offline checks, including two reproducible static ARM builds, ARM926 BusyBox applet and collector-syntax checks, exact inventory/checksum checks, and refusal of unsafe or concurrently changed output directories. Its five generated card files were byte-identical to the independently staged payload. This establishes the source assembly path; the returned card must still pass the complete backup verification below.

Use a current source checkout with hydrated Git LFS inputs and the Linux host dependencies in [Building and testing](building.md). Python, the ARM uClibc toolchain and a built static ARMv5TE/ARMv5TEJ BusyBox are required. The builder reads the Makefile-declared BusyBox source archive and configuration for its license and provenance records; it does not download or compile BusyBox itself.

From the repository root, the backup-only Makefile target can prepare the toolchain and static BusyBox without building or installing the camera runtime. Its intermediate `SOURCE/backup-kit/card/` is the legacy AP-hook payload: **keep it on the host and never copy it to this YYOS camera**. Pass only that kit's BusyBox as an input to the separate builder:

```sh
make -C SOURCE backup-kit
KIT_DIR="$PWD/SOURCE/yyos-nor-kit"
python3 tools/firmware-backup/build-yyos-kit.py \
  --busybox "$PWD/SOURCE/backup-kit/card/busybox" \
  --qemu /usr/bin/qemu-arm \
  --output "$KIT_DIR"
(cd "$KIT_DIR" && sha256sum --check SHA256SUMS)
(cd "$KIT_DIR/card" && sha256sum --check SHA256SUMS)
```

`--output` is mandatory and must name a dedicated absent or empty host directory. The builder refuses a nonempty output, including an earlier generated kit; choose a new directory for another build. Optional `--cc`, `--busybox`, `--readelf` and `--qemu` override the compiler, static BusyBox, ELF reader and ARM926 emulator. The matching environment defaults are `CC`, `BB`, `READELF` and `QEMU_ARM`. Adjust the absolute QEMU path to your host; the shown check verifies required applets and collector syntax on an ARM926 CPU.

The host package contains `card/`, `verify-backup.py`, a README, manifest, checksums and project/BusyBox licenses. Its `card/` contains exactly **`telnetd`, `busybox`, `dump.sh`, empty `yy_telnet_start` and `SHA256SUMS`**. The builder compiles its own native `telnetd` launcher from the project's C source; that filename starts no Telnet daemon. Here, `dump.sh` is [the NOR backup collector](../tools/firmware-backup/backup-nor.sh), replacing the identity-only script's role. It archives present `/appfs` and `/config` userspace trees and collects optional metadata only for exact `yy_cam` or `anyka_ipc` process names; required partition checks remain strict.

### Stage the spare card

Preserve existing recordings and previous diagnostic output privately before preparing a **clean spare FAT32 card**. The verified identity run used a writable VFAT first partition mounted by the camera at `/mnt/sdcard` from `/dev/mmcblk0p1`; other layouts have not been accepted here. Allow at least 512 MiB free for this observed 8 MiB NOR layout and its userspace snapshot; the collector independently checks its reserve. This procedure supplies no formatting or repartitioning commands.

With the camera powered off and the spare card mounted on the computer, copy `telnetd`, `busybox`, `dump.sh` and `SHA256SUMS` from **the new YYOS kit's `card/`** to the card root. Stop if any destination already exists rather than overwrite another payload. Copy the empty **`yy_telnet_start` last** to request the normal-boot entry. Do not copy the host package directory or verifier to the card root.

Do not add the legacy `_ht_ap_mode.conf` or `_ht_get_log.conf` markers, `yy_debug.ini`, `hack.sh`, factory/recovery markers or firmware-update images. Keep other runtime and debug payloads off this spare card. The normal-boot YYOS mechanism already provides the tested entry; no debug-mode startup replacement or authentication change is needed.

Use the actual mounted card path to check all five staged files, then flush and safely eject it:

```sh
CARD_MOUNT="/media/your-user/CAMERA"
(cd "$CARD_MOUNT" && sha256sum --check SHA256SUMS)
sync
```

Proceed only if every checksum check succeeds. Close file-manager windows showing the card and use the operating system's safe-eject action before removing it. These host staging checks do not prove that the camera completed a backup.

### Capture, verify and disable

1. Insert the card while the camera is powered off, then power it on and allow **about five minutes** for normal startup and collection. The collector has a 240-second monotonic budget and per-operation timeouts; an uninterruptible kernel I/O wait cannot be bounded by userspace. Do not reset, re-pair or change configuration to address a failed attempt.
2. Power the camera off before removing the card, then physically remount it on the computer. Preserve the root `backup-launcher.log` and the entire `firmware-backup/` directory in private host storage, including incomplete attempts. The log can be absent if the launcher could not establish a safe SD destination; missing output is not proof that the entry never ran.
3. Verify the selected private run with the new kit's host verifier:

```sh
python3 "$KIT_DIR/verify-backup.py" "/private/path/firmware-backup/run-TIMESTAMP-PID"
```

A verified result requires **exit status zero and `verified: true`**, with complete metadata, the userspace archive, exact partition sizes and matching independent read pairs. The observed inventory is six partitions totaling 8,388,608 bytes; an unexpected inventory requires investigation. `VERIFIED_NOR_BACKUP` in `status.txt` or a completed boot alone is insufficient. Retain all paired files and failed attempts; do not concatenate them into a guessed flash image. No successful physical backup result is recorded yet.

After copying and checking the output, disable **only the card-root `yy_telnet_start` marker** while the camera is powered off. Remove that marker or move it into an ordinary nested archive directory; keep the complete output and other kit files. Flush, safely eject and cold-boot the camera, then separately check app access, networking and normal recording. Marker removal requests that the stock startup skip this entry; it does not restore stock configuration or establish runtime/media acceptance.
