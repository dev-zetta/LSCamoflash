# LSC 3225722 / SZ F26312: investigation in progress

**LSCamoflash runtime support is not implemented or verified for this camera.** The current investigation concerns a user-owned unit labelled **SZ F26312**, article **3225722**, with app-reported firmware **V14.1.5**. Initial network checks completed on **2026-10-15**; hardware identity, SD execution, firmware backup and local streaming remain unverified on this unit. Do not install the existing Anyka or Fullhan runtime packages.

[Action's article 3225722 product page](https://www.action.com/nl-nl/p/3225722/lsc-smart-connect-draaibare-binnencamera/) identifies a rotatable indoor camera marketed with 2K video and 2.4/5 GHz Wi-Fi. This establishes the retail product reference, not its internal hardware or the compatibility of every production revision.

## What the network checks establish

A bounded check of 23 common TCP ports found only **6668** open; the other 22 probes received connection refusals. The tested ports included SSH 22, Telnet 23, HTTP 80/8080, HTTPS 443, RTSP 554/8554 and ONVIF's commonly used port 5000. No shell, web UI, RTSP stream or ONVIF service was reached through those endpoints.

The reference associates port 6668 with the Tuya LAN protocol. Here, only TCP connectivity was checked: no authenticated Tuya command or streaming capability has been demonstrated. This was not a complete port scan or proof that the firmware lacks local video support. A separate 18-second check received no camera-originated Tuya discovery datagrams and no response to one unicast ONVIF discovery probe; lack of a response does not establish that those UDP services are disabled.

## Why existing installers do not apply

The [3007325.5 Anyka profile](camera-3007325.5.md) depends on its exact stock application, boot hooks, firmware identity and media callback behavior. The newer YYOS layout and `yy_cam` described by the reference require separate inspection. A shared Anyka name or ARM926 CPU is insufficient to reuse installers, preload libraries, callback offsets, startup replacements or camera settings.

The [SZ B22705 Fullhan package](camera-sz-b22705.md) targets a different SoC, ARM architecture, stock application and SD mount layout. Its guarded management and ONVIF services are not a package for SZ F26312. Neither existing release package should be copied onto this camera's card as an exploratory installation.

## Narrow SD diagnostic plan

The [identity-only SD collector](../tools/firmware-backup/collect-yyos-identity.sh) passed 48 offline fixture checks, including 24 forced ARM926 cases with the kit's static BusyBox. The reference's [boot-chain findings](https://github.com/alex-so-3/lsc-ak3918-yyos-root/blob/06a5b1efd901db762ef74149e6ddb94bc6c254cc/docs/FINDINGS.md#boot-chain-how-the-sd-root-works) describe a normal-startup SD entry using `yy_telnet_start` and an executable named `telnetd`. Whether V14.1.5 on this unit executes that entry remains to be tested.

The candidate payload uses that entry solely to run a bounded diagnostic program and finish. The `telnetd` file is the project's existing [native backup launcher](../tools/firmware-backup/hostapd.c), renamed for the reported YYOS entry; it starts the identity collector supplied as `dump.sh` through verified file descriptors. The five SD-root files are `telnetd`, `busybox`, `dump.sh`, `yy_telnet_start` and `SHA256SUMS`. Their staged bytes passed SHA-256 readback and file/directory flush checks before the spare card was unmounted. No SD execution result is available yet.

Despite the entry's name, this payload starts no Telnet daemon or other network listener. It leaves the reference's debug-mode startup replacement unused and preserves authentication, persistent configuration, the stock application and network routes. It reads flash metadata rather than MTD device contents. The native program and BusyBox were independently verified as static ARMv5TEJ programs, with ARM926 applet and no-SD rejection checks.

The evidence is limited to CPU/kernel/memory identity, fixed startup-script snapshots and full-source hashes, the stock application's path and SHA-256, bounded optional process maps, visible flash metadata, and the mounted SD layout needed to assess a subsequent backup. The collector verifies root access and one visible writable MMC/FAT mount at `/mnt/sdcard`, reserves time within a 60-second monotonic budget, retains unique run directories and records completion or failure. Successful output includes its own SHA-256 inventory and checked file/directory flushes. Keep `backup-launcher.log` and `yyos-identity/run-*/` private; an identity-complete status is not a firmware backup result.

Existing recordings must be preserved before preparing a spare card; the camera's formatting behavior, mount path and executable compatibility must be checked rather than borrowed from another profile. Normal stock startup may itself write persistent state, even when the collector writes only to the SD card.

This draft deliberately contains no card-installation commands. A reviewed diagnostic payload, its exact inventory and a host-side validation procedure must be available before documenting a repeatable user procedure. The present plan is not a shell-enablement guide or a firmware backup result.

## Gates before backup or runtime support

| Gate | Required evidence | Current state |
| --- | --- | --- |
| Exact identity | Inspect the CPU, kernel, libc, application binary identity, mounts and stock startup path on this unit. | Pending SD diagnostic execution. |
| Compatible diagnostic entry | Confirm bounded execution, completed output and continued normal camera operation without enabling a listener. | Community mechanism identified; V14.1.5 behavior unverified. |
| Firmware backup | Inspect live NOR geometry, collect independent partition read pairs with exact lengths, and verify the complete private host copy. | Not started; the reported six-partition layout must not be assumed. |
| Storage durability | Check flush results and repeat readback after a physical SD remount. | Not tested. |
| Local media | Identify stock RTSP/ONVIF availability, authentication, codecs, audio and resource behavior through a separately reviewed procedure. | No local service reached in the initial checks. |
| LSCamoflash runtime | Implement an exact firmware guard and platform-specific integration, then verify lifecycle, media, resources and coexistence on the physical camera. | Not implemented. |

The [firmware backup guide](firmware-backup.md) and [generic collector documentation](../tools/firmware-backup/README.md) explain paired reads and host verification. Their Anyka SD launcher is not an accepted boot mechanism for this camera; do not substitute it for the planned diagnostic entry. A verified backup would still not establish whole-chip coverage, an atomic snapshot or a working restore.

Keep device firmware, configuration, credentials, recordings and raw diagnostic output in private storage. Public documentation can record reviewed identities and acceptance results without distributing those files. This investigation provides no flash-writing, recovery-image or configuration-change procedure.
