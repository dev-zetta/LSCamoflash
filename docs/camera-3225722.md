# LSC 3225722 / SZ F26312: investigation in progress

**Native streaming, authenticated management and optional key-only SSH passed short normal-cold-boot checks on this exact camera. Legacy native configuration remains blocked. The new SSH-guarded write path is under validation.** The [controlled 15-byte trial](yyos-native-media.md#guarded-15-byte-trial-bounded-acceptance) and [subsequent native-enabled normal boot](yyos-native-media.md#native-enabled-normal-boot-short-acceptance) have separate evidence. The owner accepted recorded microphone sound before that boot and confirmed Tuya app connectivity while SSH/local streams ran. The earlier 24-byte-password reboot loop, exact recovery edit and uncertain crash cause remain documented; direct VLC live playback, detailed app/recording behavior, repeated boots and long-term stability remain unresolved.

Complete camera runtime support is not implemented or verified for this **SZ F26312 / article 3225722 / V14.1.5** unit. Before the native-media attempt on **2026-10-15**, identity collection and a six-partition paired-read NOR backup passed private host verification after physical card remount, followed by short [authenticated management HTTP checks](yyos-management.md#short-live-http-acceptance). Those earlier results do not establish current camera health. Existing Anyka and Fullhan runtime packages do not apply to this camera.

[Action's article 3225722 product page](https://www.action.com/nl-nl/p/3225722/lsc-smart-connect-draaibare-binnencamera/) identifies a rotatable indoor camera marketed with 2K video and 2.4/5 GHz Wi-Fi. This establishes the retail product reference, not its internal hardware or the compatibility of every production revision.

## Recording downloads and distributable SSH build

On 2026-10-16, the recording browser was deployed through the existing SSH service while preserving the previous HTTP runtime, authentication and startup log. Root and runtime checksums passed after replacement, and stock PID 446 remained unchanged. Twelve HTTP checks passed: missing/wrong credentials returned 401, authenticated day/session/segment lists and raw/metadata downloads returned 200, HEAD returned the advertised 705,164-byte length without a body, traversal/oversized pages returned 400 and POST returned 405. The downloaded segment matched the earlier private SSH copy byte for byte. Available RAM was 16,108 KiB and HTTP RSS remained 648 KiB. Read-only downloads do not establish every stock recording/retention behavior or browser interaction.

The [host recording converter](yyos-recordings.md) preserved all 150 H.264 packets, 262 PCMU packets and every relative timestamp/payload hash in a completed sample. FFmpeg decoded the NUT output with exit 0 and empty error output. Browser playback, encrypted recordings and joined sessions are not implemented.

A redistributable static musl 1.2.6 / Dropbear 2026.94 build exposed this kernel's broken time64 syscall stub: ARM syscall 403 returned success without touching its output buffer. A narrow userspace clock adapter now converts the working typed ARM time32 clock result into libc time64, preserving monotonic deadlines; Dropbear exits if that clock fails. The final 230,948-byte SSH binary SHA256 is `99facab1154cff679a7c5cd48e0239fd839b86e1779bee00f62e5b5342b6efa6`. Actual camera probes passed clock progression, file metadata, fork/TLS/random and bounded poll/select waits. A separate temporary port 2223 server passed owner-key root login, PTY, wrong-key/password-method refusal and owned cleanup with 252 KiB RSS / one thread. The original SSH service stayed intact; normal boot with this replacement build remains a separate acceptance step. Earlier failed clock/PTY build controls are retained privately.

## What the network checks establish

A bounded check of 23 common TCP ports found only **6668** open; the other 22 probes received connection refusals. The tested ports included SSH 22, Telnet 23, HTTP 80/8080, HTTPS 443, RTSP 554/8554 and ONVIF's commonly used port 5000. No shell, web UI, RTSP stream or ONVIF service was reached through those endpoints.

The reference associates port 6668 with the Tuya LAN protocol. The initial probes checked only TCP connectivity, not authenticated commands or streaming. They were not a complete port scan or proof that the firmware lacks local video support. A separate 18-second check received no camera-originated Tuya discovery datagrams and no response to one unicast ONVIF discovery probe; lack of a response does not establish that those UDP services are disabled.

Before native configuration, verified-backup credential recovery and the public [native-media helper](yyos-native-media.md) successfully performed authenticated, read-only Tuya 3.5 status, reporting **DP237 false / DP239 false**. The dashboard also reported no native listeners at that earlier sample. The subsequent approved 24-byte-password attempt returned `invalid_status_response` and was followed by the observed reboot loop. Production configuration now returns `native_enablement_blocked_boot_loop` before opening a transport. Recovery later verified both configuration enable flags changed from 1 to 0 while preserving password bytes; the off state was observed through one normal cold boot. The separate bounded 15-byte trial below supplies later native authentication/media observations.

On the later recovery boot, authenticated status reported **DP237 false / DP239 true**, with no native listeners observed. HTTP returned 401 unauthenticated and 200 authenticated; stock app/management were reported running, and uptime advanced by 84 seconds without a restart during that observation. A password-set flag does not verify its value or authentication behavior. Returned private evidence now verifies the exact two-byte edit and one stock launch; normal-bootstrap status also remained false/true after one cold boot. Production native configuration remains blocked.

After normal-bootstrap restoration, uptime increased from **137 to 444 seconds** across a further **307-second** observation, with stock app/management running and both native listeners absent; available RAM was **16,836 KiB** at the second sample. The owner reported Online and steady. Independent static review then confirmed 16-byte stock native password caches with unbounded copies and 24-byte values in the preserved pre-recovery configuration: a strong crash candidate, but not a proven crash path. The [native helper](yyos-native-media.md#why-legacy-configuration-is-disabled) now caps new passwords at 15 bytes while keeping public activation blocked; the separate controlled trial below does not remove that block.

A later separately controlled 15-byte trial ran once. Its retained result failed at final status, but fresh authenticated status and direct media checks independently established services enabled. Both H.264 streams and PCMU 8 kHz mono audio decoded for five seconds over TCP and UDP; RTSP anonymous/wrong-password requests were rejected, and native ONVIF accepted correct WSSE while rejecting missing/wrong credentials. Only the first main-TCP audio sample was nonzero; audible microphone sound was confirmed in a later recorded sample. HTTP status reached uptime 1,324 seconds with stock/management and both listeners running. The returned trial card was privately verified and its temporary startup archived on 2026-10-16, then normal startup and optional SSH were staged while powered off. See the [bounded trial record](yyos-native-media.md#guarded-15-byte-trial-bounded-acceptance) for counts, authentication limits and the preserved ambiguous result.

The subsequent **native-enabled normal cold boot passed short live checks on 2026-10-16**. SSH verified the exact stock binary/root hook, absent debug entry and empty normal marker; owner-key root/PTY access and a checked 32 KiB SD round trip passed. Stock PID 446 remained unchanged across uptime 609.49→1,112.53 seconds. HTTP returned anonymous 401/authenticated 200, both native TCP streams decoded again, and RTSP Digest/ONVIF WSSE authorization controls passed again. Available RAM was 16,252 then 16,576 KiB out of 38,112; SSH master RSS was 292 KiB. The owner confirmed the Tuya app Online alongside SSH/local streams. The [normal-boot record](yyos-native-media.md#native-enabled-normal-boot-short-acceptance) distinguishes connectivity from all app functions and zero-valued post-boot audio from the earlier audible recording. The legacy path remains blocked; the new explicit SSH-guarded implementation now checks active services, both flags/listeners and fresh live identity, with its write sequence awaiting physical acceptance.

## Why existing installers do not apply

The [3007325.5 Anyka profile](camera-3007325.5.md) depends on its exact stock application, boot hooks, firmware identity and media callback behavior. The collected YYOS-style layout and `yy_cam` application require separate integration. A shared Anyka name or ARM926 CPU is insufficient to reuse installers, preload libraries, callback offsets, startup replacements or camera settings.

The [SZ B22705 Fullhan package](camera-sz-b22705.md) targets a different SoC, ARM architecture, stock application and SD mount layout. Its guarded management and ONVIF services are not a package for SZ F26312. Neither existing release package should be copied onto this camera's card as an exploratory installation.

## Verified identity-only SD diagnostics

The [identity-only SD collector](../tools/firmware-backup/collect-yyos-identity.sh) passed 48 offline fixture checks, including 24 forced ARM926 cases with the kit's static BusyBox, before the first physical run. That run confirmed the normal-startup SD entry described by the reference's [boot-chain findings](https://github.com/alex-so-3/lsc-ak3918-yyos-root/blob/06a5b1efd901db762ef74149e6ddb94bc6c254cc/docs/FINDINGS.md#boot-chain-how-the-sd-root-works). Inspection of this unit's collected startup script independently confirmed the `yy_telnet_start` / `telnetd` entry at lines 78–79; normal startup also conditionally launches `yy_cam` when the stock NVRAM `STATUS` is `active`.

The tested payload uses that entry solely to run a bounded diagnostic program and finish. The `telnetd` file is the project's existing [native backup launcher](../tools/firmware-backup/hostapd.c), renamed for the YYOS entry; it starts the identity collector supplied as `dump.sh` through verified file descriptors. The five SD-root files are `telnetd`, `busybox`, `dump.sh`, `yy_telnet_start` and `SHA256SUMS`. Their staged bytes passed SHA-256 readback and file/directory flush checks before the spare card was unmounted.

Despite the entry's name, this payload starts no Telnet daemon or other network listener. It leaves the reference's debug-mode startup replacement unused and does not change authentication or persistent configuration, stop the stock application or alter network routes. It reads flash metadata rather than MTD device contents. The native program and BusyBox were independently verified as static ARMv5TEJ programs, with ARM926 applet and no-SD rejection checks.

The evidence is limited to CPU/kernel/memory identity, fixed startup-script snapshots and full-source hashes, the stock application's path and SHA-256, bounded optional process maps, visible flash metadata, and the mounted SD layout needed to assess a subsequent backup. The collector verifies root access and one visible writable MMC/FAT mount at `/mnt/sdcard`, reserves time within a 60-second monotonic budget, retains unique run directories and records completion or failure. Successful output includes its own SHA-256 inventory and checked file/directory flushes. Keep `backup-launcher.log` and `yyos-identity/run-*/` private; an identity-complete status is not a firmware backup result.

On the first successful boot, the native entry recorded **UID 0 / root**, the accepted `/mnt/sdcard` mount from `/dev/mmcblk0p1`, and **`CHILD_EXIT=0`**. The collector recorded **`IDENTITY_COLLECTION_COMPLETE`**. After the card was physically removed, remounted on the computer and copied to private host storage, **101 checksummed files** passed verification. The owner reported that the camera stayed online during the two-minute attempt and that the app recognized the card's capacity. These observations establish diagnostic execution and identity-output readback; they do not establish streaming, a complete recording test or a firmware backup.

Existing recordings must be preserved before preparing a spare card; the camera's formatting behavior, mount path and executable compatibility must be checked rather than borrowed from another profile. Normal stock startup may itself write persistent state, even when the collector writes only to the SD card.

The public files linked here are the project's collector and launcher source; the captured stock scripts, maps and other device output remain private. This guide contains no shell-enablement or flash-writing procedure. A repeatable firmware backup requires the separate collection and verification steps below.

The identity payload collected no MTD contents. A subsequent NOR run recorded root launcher **`CHILD_EXIT=0`** and collector status **`VERIFIED_NOR_BACKUP`**. The owner reported that the camera stayed online in the app and behaved normally throughout the five-minute backup attempt. ## Build a separate YYOS NOR kit

The successful backup and its procedure below preceded the native configuration failure. Preserve that verified private backup; the NOR kit is not a boot-loop recovery payload, and the affected camera should not be booted with it as a substitute for a reviewed recovery procedure.

The [YYOS builder](../tools/firmware-backup/build-yyos-kit.py) creates a separate host-side package for the generic paired-read NOR collector. The successful physical backup used independently checked native/BusyBox components and a freshly staged collector. All five generated builder card files are **byte-identical to that physically tested payload**; the rest of the host package stays on the computer. This acceptance applies to the exact camera, app-reported firmware and application identity above, not every YYOS model.

The collector passed **80 focused tests**, and the builder passed **nine offline checks**, including two reproducible static ARM builds, ARM926 BusyBox applet and collector-syntax checks, exact inventory/checksum checks, and refusal of unsafe or concurrently changed output directories. These establish source behavior and assembly; every new capture must still pass the complete backup verification below.

Use a current source checkout with hydrated Git LFS inputs and the Linux host dependencies in [Building and testing](building.md). Python, the ARM uClibc toolchain and a built static ARMv5TE/ARMv5TEJ BusyBox are required. The builder reads the Makefile-declared BusyBox source archive and configuration for its license and provenance records; it does not download or compile BusyBox itself.

From the repository root, the backup-only Makefile target can prepare the toolchain and static BusyBox without building or installing the camera runtime. Its intermediate `SOURCE/backup-kit/card/` is the legacy AP-hook payload: **keep it on the host and never copy it to this YYOS camera**. Pass only that kit's BusyBox as an input to the separate builder:

```sh
make -C SOURCE backup-kit
KIT_DIR="$PWD/SOURCE/yyos-nor-kit"
python3 tools/firmware-backup/build-yyos-kit.py \
  --busybox "$PWD/SOURCE/backup-kit/card/busybox" \
  --qemu /usr/bin/qemu-arm \
  --output "$KIT_DIR"
(cd "$KIT_DIR" && sha256sum --check SHA256SUMS)
(cd "$KIT_DIR/card" && sha256sum --check SHA256SUMS)
```

`--output` is mandatory and must name a dedicated absent or empty host directory. The builder refuses a nonempty output, including an earlier generated kit; choose a new directory for another build. Optional `--cc`, `--busybox`, `--readelf` and `--qemu` override the compiler, static BusyBox, ELF reader and ARM926 emulator. The matching environment defaults are `CC`, `BB`, `READELF` and `QEMU_ARM`. Adjust the absolute QEMU path to your host; the shown check verifies required applets and collector syntax on an ARM926 CPU.

The host package contains `card/`, `verify-backup.py`, a README, manifest, checksums and project/BusyBox licenses. Its `card/` contains exactly **`telnetd`, `busybox`, `dump.sh`, empty `yy_telnet_start` and `SHA256SUMS`**. The builder compiles its own native `telnetd` launcher from the project's C source; that filename starts no Telnet daemon. Here, `dump.sh` is [the NOR backup collector](../tools/firmware-backup/backup-nor.sh), replacing the identity-only script's role. It archives present `/appfs` and `/config` userspace trees and collects optional metadata only for exact `yy_cam` or `anyka_ipc` process names; required partition checks remain strict.

### Stage the spare card

Preserve existing recordings and previous diagnostic output privately before preparing a **clean spare FAT32 card**. The verified identity run used a writable VFAT first partition mounted by the camera at `/mnt/sdcard` from `/dev/mmcblk0p1`; other layouts have not been accepted here. Allow at least 512 MiB free for this observed 8 MiB NOR layout and its userspace snapshot; the collector independently checks its reserve. This procedure supplies no formatting or repartitioning commands.

With the camera powered off and the spare card mounted on the computer, copy `telnetd`, `busybox`, `dump.sh` and `SHA256SUMS` from **the new YYOS kit's `card/`** to the card root. Stop if any destination already exists rather than overwrite another payload. Copy the empty **`yy_telnet_start` last** to request the normal-boot entry. Do not copy the host package directory or verifier to the card root.

Do not add the legacy `_ht_ap_mode.conf` or `_ht_get_log.conf` markers, `yy_debug.ini`, `hack.sh`, factory/recovery markers or firmware-update images. Keep other runtime and debug payloads off this spare card. The normal-boot YYOS mechanism already provides the tested entry; no debug-mode startup replacement or authentication change is needed.

Use the actual mounted card path to check all five staged files, then flush and safely eject it:

```sh
CARD_MOUNT="/media/your-user/CAMERA"
(cd "$CARD_MOUNT" && sha256sum --check SHA256SUMS)
sync
```

Proceed only if every checksum check succeeds. Close file-manager windows showing the card and use the operating system's safe-eject action before removing it. These host staging checks do not prove that the camera completed a backup.

### Capture, verify and disable

1. Insert the card while the camera is powered off, then power it on and allow **about five minutes** for normal startup and collection. The collector has a 240-second monotonic budget and per-operation timeouts; an uninterruptible kernel I/O wait cannot be bounded by userspace. Do not reset, re-pair or change configuration to address a failed attempt.
2. Power the camera off before removing the card, then physically remount it on the computer. Preserve the root `backup-launcher.log` and the entire `firmware-backup/` directory in private host storage, including incomplete attempts. The log can be absent if the launcher could not establish a safe SD destination; missing output is not proof that the entry never ran.
3. Verify the selected private run with the new kit's host verifier:

```sh
python3 "$KIT_DIR/verify-backup.py" "/private/path/firmware-backup/run-TIMESTAMP-PID"
```

A verified result requires **exit status zero and `verified: true`**, with complete metadata, the userspace archive, exact partition sizes and matching independent read pairs. The observed inventory is six partitions totaling 8,388,608 bytes; an unexpected inventory requires investigation. `VERIFIED_NOR_BACKUP` in `status.txt` or a completed boot alone is insufficient. Retain all paired files and failed attempts; do not concatenate them into a guessed flash image. The physical result above is evidence for that run, not a substitute for verifying a new capture.

After copying and checking the output, disable **only the card-root `yy_telnet_start` marker** while the camera is powered off. Remove that marker or move it into an ordinary nested archive directory; keep the complete output and other kit files. Flush, safely eject and cold-boot the camera, then separately check app access, networking and normal recording. Marker removal requests that the stock startup skip this entry; it does not restore stock configuration or establish runtime/media acceptance.

After the accepted capture, only that marker was archived into a nested diagnostic directory. Its root path was confirmed absent, all staged input hashes were unchanged, the backup output and `DCIM` recordings were preserved, and file/directory flushes returned success. A subsequent cold-boot/recording acceptance check remains separate from this completed host-side disable operation.
